After this page you can read the `scanScope` section of any report and say
exactly which directories were allowed to vouch for a given layer's keys — and
why a usage somewhere else in the repository did not count.

## What the Graph Is

The **consumer graph** is the set of edges from apps to the layers they consume.
An app contributes three things to it:

| Field | Means |
|---|---|
| `name` | The app's name, as it appears in reports |
| `rootDir` | The app's code root |
| `layers` | The layers it consumes, in precedence order — earlier entries override later ones at runtime |

From those edges plus the resolved layers ([what a layer is](/monorepos/layers)),
the tool derives four answers, with no name matching anywhere:

- the **canonical layers** — every layer that owns its locale directory, aliases excluded
- **which apps use a layer** — alias names on both sides resolve to their owner first
- **which layers an app uses** — again alias-resolved, dropping layers with no locale directory
- the **shared layers** — canonical layers consumed by more than one app

Nothing here touches the filesystem. It is a derivation over the configuration
you can print with `the-i18n-cli detect`.

## Where the Edges Come From

::warning
Consumption edges are derived today only for Nuxt projects, where each app
reports the layers it extends and the apps are merged into one project config.
The Laravel, Vue, React/Next and generic adapters each resolve a single app that
consumes all of their layers. On those stacks the scoping below is still
applied, but every layer's scope is the whole project — the same behavior as an
unscoped scan. You get per-layer reports and duplicate detection; you do not get
app-scoped usage evidence, because nothing in the project declares which app
consumes what.
::

## Why the Graph Decides What "Used" Means

A key lives in one layer. At runtime, only apps that consume that layer can
resolve it. So a reference to `checkout.cart.title` inside an admin app that
does not consume the checkout layer is not evidence that the key is needed —
it is evidence of a bug, and treating it as usage would keep a dead key alive
forever, or worse, keep a broken call site invisible.

That is the whole reason the scan is scoped: **usage counts only from the code
of the apps that consume the layer**. Everything else on this page is the
machinery that makes that sentence true.

## How a Scan Is Planned

Before scanning, the tool builds a plan from the graph:

1. **Units.** Each distinct app root directory and each canonical layer root
   directory becomes one scan unit with a stable name. Where an app and a layer
   share a directory, the app's name wins.
2. **Carve-outs.** When one unit's directory nests inside another's, the nested
   subtree is excluded from the ancestor's scan. Every file is attributed to
   exactly one unit, so a scoped scan reads no more files than one whole-project
   scan would.
3. **A project-root unit.** If the project directory lies outside every unit —
   the usual case for a monorepo root holding `scripts/` or `tools/` — a
   synthetic `project-root` unit claims it, and that unit counts for *every*
   layer. Code outside all apps can therefore never turn into a false orphan.
4. **Per-layer scope.** A layer's scope is its own root directory plus the root
   directories of every app that consumes it, plus the project-root unit when
   there is one.

Each unit is scanned once; layers with overlapping scopes reuse the same
evidence rather than rescanning.

## Reading `scanScope`

`remove-orphans` and `find_orphan_keys` report the effective scope per layer,
relative to the project directory, so the scoping is auditable rather than
implied:

```json
{
  "scanScope": {
    "root": [".", "app-admin", "app-shop"],
    "app-admin": ["app-admin"],
    "app-shop": ["app-shop"]
  }
}
```

Read it as: the shared `root` layer was checked against both apps and the
repository root, while each app-private layer was checked against its own app
only. A key defined in `app-admin` and referenced only from `app-shop` is
outside `app-admin`'s scope — that is a
[misplaced usage](/monorepos/misplaced-usages), reported separately and never
removed.

## Degenerate Cases, and Why They Are Safe

Scoping is allowed to widen a layer's scope, never to narrow it wrongly:

| Situation | Effect |
|---|---|
| No app information at all | Every layer is checked against every unit, and every layer counts as shared |
| A layer consumed by no app | Checked against every unit |
| A single-app project | The app's scope is the whole project, so per-layer scope equals the whole project |
| Explicit scan directories | All layers are checked against one combined usage set from those directories, and misplaced-usage detection is off |

The last row is the manual override: `scanDirs` on the `find_orphan_keys` and
`remove_orphan_keys` MCP tools, and on the same functions in the programmatic
API. It is not a CLI flag — from the terminal, scoping is derived, and the way
to narrow a run is `--layer`.

## Per-Layer Scanning

Layers are the unit of work everywhere, not only in the plan:

- `the-i18n-cli remove-orphans --layer ui` checks one layer, against that
  layer's scope. Without `--layer`, every non-alias layer is checked, each
  against its own scope, in one pass.
- Reports are keyed by layer: `orphanKeys`, `uncertainKeys` and `removed` are
  all maps from layer name to keys, and `find_orphan_keys` adds
  `summary.layersChecked` naming the layers that ran.
- `orphanScan` in the project config is keyed by layer name too, so a family of
  runtime-built keys can be declared dynamic in the layer that owns it:

```ts [i18n-kit.config.ts]
import { defineI18nKitConfig } from '@the-i18n-kit/cli/config'

export default defineI18nKitConfig({
  orphanScan: {
    ui: { ignorePatterns: ['ui.icons.*'] },
  },
})
```

A key in `orphanScan` that matches no detected layer silently applies to
nothing, so the CLI warns on stderr and lists the layer names it did detect.

## Limits

- The graph is only as good as what the project declares. An app that consumes a
  layer through a mechanism the adapter cannot see is missing an edge, and its
  usages will read as misplaced.
- Scope is directory-based. Two apps sharing one root directory cannot be told
  apart.
- Layer precedence comes from the order an app lists its layers. Where two apps
  disagree about the order of the same two layers, the first one seen wins —
  which matters for [duplicate detection](/monorepos/duplicates-and-divergence),
  not for scoping.
