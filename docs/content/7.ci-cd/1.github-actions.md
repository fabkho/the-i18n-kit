## Gate a Pull Request

No action needed: run the CLI and let its exit code decide the job.

```yaml [.github/workflows/i18n.yml]
name: i18n

on: pull_request

jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: Fail on keys that would render raw
        run: npx -y @the-i18n-kit/cli@latest check

      - name: Fail when coverage drops below 90%
        run: npx -y @the-i18n-kit/cli@latest status --fail-under 90
```

Both steps fail the job with exit `2` on findings. `check` alone is the gate worth
having on day one: it needs no config file and no API key. Every gate flag is on
the [agent contract](/getting-started/agent-contract#gates).

## Translate and Open a Pull Request

The composite action installs `@the-i18n-kit/cli` on the runner, runs
[`translate`](/reference/cli/translate), and opens a pull request with whatever
the run wrote. Every input and output is generated from `action.yml` in the
[action reference](/reference/action).

```yaml [.github/workflows/i18n-translate.yml]
name: i18n translate

on:
  pull_request:
    paths:
      - 'i18n/locales/en.json'

permissions:
  contents: write
  pull-requests: write

jobs:
  translate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: fabkho/the-i18n-kit@main
        with:
          provider: google
          model: gemini-2.5-flash
          api_key: ${{ secrets.GEMINI_API_KEY }}
          layer: common
```

Three things there are load-bearing:

- **`actions/checkout@v4` first.** The action runs against the working directory
  and commits from it.
- **`contents: write` and `pull-requests: write`.** The action pushes a branch and
  calls `gh pr create`. Repositories can also disable pull request creation by
  Actions entirely, under Settings → Actions → General; with that off, the step
  fails however the token is scoped.
- **`layer`.** Required, and always passed to the CLI. Run `the-i18n-cli status`
  to see the names your project resolves — projects with one locale directory
  usually have one layer named `root`.

Pin the action to a tag once you have a version you trust. `cli_version: skip`
skips the install step when an earlier step already put the CLI on the `PATH`.

The pull request is opened on a new branch named
`i18n/translate-missing-<unix-timestamp>`, against `base_branch` or the triggering
ref, with a commit message and title naming the provider and the layer. All of
that is overridable through the [inputs](/reference/action). When the run wrote
nothing, no pull request is opened and `pr_url` comes back empty.

::warning
The commit stages the whole working directory, not only locale files. If an
earlier step in the same job builds or formats the checkout, those changes land in
the translation pull request. Give the action its own job, or its own
`working_directory`.
::

## When the Job Fails

| Situation | Exit | What the action does |
|---|---|---|
| Everything translated | `0` | Opens the pull request, job green |
| Some keys failed, `fail_on_failed` off (default) | `0` | Opens the pull request, warns with the count, job green |
| Some keys failed, `fail_on_failed: true` | `2` | Records `gate_tripped`, **still opens the pull request**, then fails the job |
| Nothing translated at all — unusable API key, unknown provider, unreadable project | `1` | Fails the translate step, no pull request |
| Branch push or `gh pr create` rejected | non-zero | Fails the pull request step — check the permissions above |

A tripped gate never costs you the translations: the commit and the pull request
happen first, and only a final step exits `2`. Partial failures are not a gate by
default — the keys that failed stay missing and the next run retries them. Set
`fail_on_failed: true` when you would rather see that as a red job.

The `translated_count` and `failed_count` outputs are for logs and downstream
steps; they never decide the job outcome.
