Point the CLI at a directory and it decides which adapter resolves your locales. Five adapters ship: `nuxt`, `laravel`, `generic`, `vue` and `react`.

An **adapter** is the per-framework detection and resolution logic: it recognizes a project, finds its locale directories, and reports its locales, its default locale and its layers. A **layer** is a scoped locale directory — a Nuxt layer, a workspace package, a shared UI library, or one app in a monorepo.

If the wrong adapter is chosen, [pin one](#forcing-an-adapter) with `framework`.

## Declaring the Paths Settles It

Declare both `localeDirs` and `defaultLocale` in your project config and the generic adapter resolves the project, whatever the dependency list says. **If you write down where your locale files are, that is where they are.**

Project configuration is read from `i18n-kit.config.ts` (also `.mts`, `.js`, `.mjs`, `.cjs`) and `.i18n-mcp.json`, both looked up from the project directory upwards, the way `eslint` and `tsconfig` resolve theirs. A key declared in both files is an error naming both, not a silent merge.

```ts [i18n-kit.config.ts]
import { defineI18nKitConfig } from '@the-i18n-kit/cli/config'

export default defineI18nKitConfig({
  defaultLocale: 'en',
  localeDirs: ['src/locales', { path: 'packages/ui/locales', layer: 'ui' }],
})
```

See [Generic](/frameworks/generic) for what the generic adapter does with those paths.

## Forcing an Adapter

Set `framework` to an adapter name. Detection is then skipped entirely — no adapter's `detect` runs, and the named adapter resolves the project:

```ts [i18n-kit.config.ts]
import { defineI18nKitConfig } from '@the-i18n-kit/cli/config'

export default defineI18nKitConfig({
  framework: 'vue',
})
```

The same key works in `.i18n-mcp.json`:

```json [.i18n-mcp.json]
{
  "framework": "laravel"
}
```

Valid values are `nuxt`, `laravel`, `vue`, `react` and `generic`. A name that matches no adapter fails with an error listing the ones that exist, rather than falling back to guessing.

Forcing is worth reaching for when a repository carries signals for two frameworks — a Laravel backend with a Vue frontend in one checkout is the common case — or when you want the resolution behavior of one adapter regardless of what the dependency list says.

## What Detection Will Not Do

Detection never executes any of your config files. It reads `package.json` and `composer.json`, checks for files on disk, and pattern-matches file contents. Executing a framework config happens only in the winning adapter's resolution step, and only for the adapters that document it — see [Vue](/frameworks/vue) and [React / Next.js](/frameworks/react-next).

## Seeing the Decision

`the-i18n-cli init` reports which adapter matched, and whether it derives locale configuration for itself — false only for `generic`, which cannot resolve without the paths you declare.

`the-i18n-cli detect` prints the resolved configuration, including the adapter name under `framework`.

Both accept `--projectDir` (`-d`) to point at a directory other than the working directory.

::note
Resolution is cached per project directory for the life of the process. Editing a framework config while a long-running MCP session is open does not re-detect; restart it.
::

For the signals each adapter adds up and how ties are broken, see [how detection scores adapters](/extra-topics/detection-scoring).
