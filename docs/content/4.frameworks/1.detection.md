---
title: Confidence-Scored Detection
description: How the CLI picks an adapter for your project, why explicit configuration wins, and how to force one adapter outright.
---

Point the CLI at a directory and it decides which adapter resolves your locales. This page explains how that decision is made, how to read the score it reports, and how to take the decision yourself.

An **adapter** is the per-framework detection and resolution logic: it recognizes a project, finds its locale directories, and reports its locales, its default locale and its layers. A **layer** is a scoped locale directory — a Nuxt layer, a workspace package, a shared UI library, or one app in a monorepo. Five adapters ship: `nuxt`, `laravel`, `generic`, `vue` and `react`.

## The Highest Score Wins

Detection runs every registered adapter's `detect` against your project directory, concurrently. Each returns a number. Adapters scoring zero are discarded, the rest are ranked, and the highest one resolves the project.

Scores are not percentages. They are sums of signals, and each adapter has its own ceiling:

| Adapter | Signals it adds up | Highest reachable |
|---|---|---|
| `generic` | `localeDirs` and `defaultLocale` both declared in your project config — a flat 10, or 0 | 10 |
| `react` | `next` (5) or `react` + `react-dom` (3); an i18n dependency (+2); a `next.config` alongside `next` (+1); a probed locale directory holding JSON (+2) | 10 |
| `vue` | `vue` present (2); `vue-i18n` (+3); a probed locale directory holding JSON (+2) | 7 |
| `laravel` | `artisan` (+2); `laravel/framework` in `composer.json` (+2); a `lang/` directory with locale content (+1) | 5 |
| `nuxt` | A Nuxt config mentioning `i18n`, or child Nuxt apps that do (2); a Nuxt config without either (1) | 2 |

Nuxt's ceiling of 2 never costs it a project, because the adapters that could outscore it exclude themselves first: the Vue adapter scores 0 when `nuxt` or `@nuxt/kit` is a dependency or a `nuxt.config.{ts,js,mjs}` exists, and the React adapter scores 0 on the same Nuxt signals plus `vue`. The frameworks that overlap rule each other out, so the numbers only ever compare adapters that could both be right.

Equal scores are broken by registration order, which is `nuxt`, `laravel`, `generic`, `vue`, `react`.

If an adapter throws while detecting, the failure is logged as a warning and that adapter scores 0 — one broken `package.json` does not take the whole run down. If no adapter scores above zero, the command fails with an error naming the directory and listing the registered adapters.

## Explicit Configuration Outscores Inference

The generic adapter scores 10 whenever your project config declares both `localeDirs` and `defaultLocale`, and 0 otherwise. Nothing an adapter infers exceeds that, and on the one tie it can reach — a Next.js project with every signal present — registration order still puts `generic` ahead of `react`.

That is the mechanism behind a plain statement: **if you write down where your locale files are, that is where they are.** No dependency list or directory layout overrides it.

Project configuration is read from `i18n-kit.config.ts` (also `.mts`, `.js`, `.mjs`, `.cjs`) and `.i18n-mcp.json`, both looked up from the project directory upwards, the way `eslint` and `tsconfig` resolve theirs. A key declared in both files is an error naming both, not a silent merge.

```ts [i18n-kit.config.ts]
import { defineI18nKitConfig } from '@the-i18n-kit/cli/config'

export default defineI18nKitConfig({
  defaultLocale: 'en',
  localeDirs: ['src/locales', { path: 'packages/ui/locales', layer: 'ui' }],
})
```

See [Generic](/frameworks/generic) for what the generic adapter does with those paths.

## Forcing an Adapter

Set `framework` to an adapter name. Detection is then skipped entirely — no adapter's `detect` runs, and the named adapter resolves the project:

```ts [i18n-kit.config.ts]
import { defineI18nKitConfig } from '@the-i18n-kit/cli/config'

export default defineI18nKitConfig({
  framework: 'vue',
})
```

The same key works in `.i18n-mcp.json`:

```json [.i18n-mcp.json]
{
  "framework": "laravel"
}
```

Valid values are `nuxt`, `laravel`, `vue`, `react` and `generic`. A name that matches no adapter fails with an error listing the ones that exist, rather than falling back to guessing.

Forcing is worth reaching for when a repository carries signals for two frameworks — a Laravel backend with a Vue frontend in one checkout is the common case — or when you want the resolution behavior of one adapter regardless of what the dependency list says.

## What Detection Will Not Do

`detect` never executes any of your config files. It reads `package.json`, `composer.json`, checks for files on disk, and pattern-matches file contents — nothing more. Detection runs against every project the CLI is pointed at, including ones the adapter will lose, so running a stranger's `vite.config.ts` to lose a scoring contest is not a trade the tool makes.

Executing framework config happens only in the winning adapter's resolution step, and only for the adapters that document it — see [Vue](/frameworks/vue) and [React / Next.js](/frameworks/react-next).

## Seeing the Decision

`the-i18n-cli init` reports which adapter matched, with what score, and which other adapters also scored, so you can tell why `nuxt` was chosen over `generic` rather than inferring it from the output. It also reports whether the matched adapter derives locale configuration for itself — false only for `generic`, which cannot resolve without the paths you declare.

`the-i18n-cli detect` prints the resolved configuration, including the adapter name under `framework`.

Both accept `--projectDir` (`-d`) to point at a directory other than the working directory.

::note
Resolution is cached per project directory for the life of the process. Editing a framework config while a long-running MCP session is open does not re-detect; restart it.
::
