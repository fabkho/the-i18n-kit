title: Where Configuration Lives
description: The three places kit policy can be declared, how each one reaches the CLI, and how to choose between them.

Kit policy — the things you tell the tool that it cannot see for itself — can be
declared in three places. This page shows what each one is, how the value gets
from the file into a running command, and which to pick.

This page is about location, not fields. Every field, with its type, its
constraints and where it may be declared, is in the
[configuration field reference](/configuration/reference).

## The Three Places

| Where | Applies | Requires |
|---|---|---|
| `i18n-kit.config.ts` | Immediately, from the file on disk | Nothing beyond the CLI |
| `.i18n-mcp.json` | Immediately, from the file on disk | Nothing beyond the CLI |
| `i18nKit` in `nuxt.config.ts` | After a build has produced the artifact | `@the-i18n-kit/nuxt`, and Nuxt |

The two files accept the same field names and validate against one shared zod
schema, with a type-level guard that fails the CLI build if the schema and the
documented config type drift apart. The `i18nKit` block is typed by the Nuxt
module's own interface, which names a subset of the same keys.

### `i18n-kit.config.ts`

A TypeScript file that exports its config as the default export:

```ts [i18n-kit.config.ts]
import { defineI18nKitConfig } from '@the-i18n-kit/cli/config'

export default defineI18nKitConfig({
  context: 'A B2B booking platform.',
  glossary: { anny: 'Brand name. NEVER translate.' },
  protectedLocales: ['de-formal'],
})
```

`defineI18nKitConfig` returns its argument unchanged. Its entire job is the
type: `protectedLocales` autocompletes, and a misspelled `protectedLocals` is a
red squiggle while you write it rather than a failed command later.

Five other extensions are accepted, so a JavaScript project does not have to
adopt TypeScript to get a checked config: `.mts`, `.js`, `.mjs`, `.cjs` and
`.cts`. If a directory contains more than one, the CLI uses the first in that
order — `.ts` first — and warns, naming the files it ignored.

::warning
The import specifier matters when the CLI runs through `npx` in a project that
never installed it. The CLI aliases the legacy specifier `the-i18n-cli/config`
to the copy of `defineI18nKitConfig` that is already running, so a config file
importing that name loads with nothing installed. `@the-i18n-kit/cli/config` is
resolved normally, so it needs the package present — otherwise the config fails
to load with `Cannot find module '@the-i18n-kit/cli/config'`. Import the scoped
name when the package is a project dependency; use `the-i18n-cli/config` for
configs that must load under a bare `npx`.
::

### `.i18n-mcp.json`

The original format, still supported and still what `the-i18n-cli init` writes.
It accepts the same keys, plus a `$schema` pointer for editor completion:

```json [.i18n-mcp.json]
{
  "$schema": "node_modules/@the-i18n-kit/mcp/schema.json",
  "context": "A B2B booking platform.",
  "glossary": { "anny": "Brand name. NEVER translate." },
  "protectedLocales": ["de-formal"]
}
```

### `i18nKit` in `nuxt.config.ts`

With `@the-i18n-kit/nuxt` installed, policy sits next to the i18n config it
talks about, typed by the module's own options interface:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxtjs/i18n', '@the-i18n-kit/nuxt'],

  i18nKit: {
    context: 'A B2B booking platform.',
    glossary: { anny: 'Brand name. NEVER translate.' },
    localeNotes: { 'de-formal': 'Formal German (Sie).' },
  },
})
```

Eleven keys are accepted here — everything Nuxt cannot work out for itself. The
keys it can work out (`locales`, `localeDirs`, `defaultLocale`) are owned by the
module and rejected, so they cannot become a second source of truth. That split
is the subject of [declared vs. derived config](/configuration/declared-vs-derived).

## How Each One Reaches a Command

Both files are read directly from disk. Every adapter funnels through one
loader, `loadProjectConfig`, which searches from the project directory upward
for the nearest `i18n-kit.config.*` and the nearest `.i18n-mcp.json` — the way
ESLint, Prettier and `tsconfig.json` resolve theirs. The search stops at the
first directory that has one, so a config in an app directory shadows one at the
repository root rather than merging with it.

`nuxt.config.ts` is different, and the difference is the whole reason the typed
config exists. The CLI never loads your Nuxt config to read policy out of it.
The module publishes what Nuxt resolved to `.nuxt/i18n-kit.json` during the
build, and the CLI reads that file. Policy declared only in `nuxt.config.ts`
therefore does not exist for the CLI until something has been built.

## Why No Build Step Is Load-Bearing

For `context` or `glossary`, policy that goes missing in an unbuilt checkout
costs a little quality in a prompt. For the two keys that *suppress* work, it
costs correctness:

- `protectedLocales` excludes locales from automatic translation. Unread, a
  locale someone marked as human-maintained goes back into the machine
  translation target set.
- `orphanScan` narrows what counts as an orphan key — a key defined with no
  usage evidence in any consuming app.

A fresh clone that has never run `nuxt prepare` has no artifact. Neither does a
CI job that runs the kit before the build, or a container that only mounted the
repository. In each of those, `protectedLocales: ['de-formal']` sitting visibly
in `nuxt.config.ts` applies to nothing.

The module warns at build time when either key is declared in `nuxt.config.ts`
and nowhere else:

```text
protectedLocales declared only in nuxt.config.ts. The CLI reads it from the
generated artifact, so a checkout that has not been built will not apply it.
Keep it in .i18n-mcp.json if that matters — the CLI reads that directly.
```

A warning is not a fix. `i18n-kit.config.ts` is: it is executed from source, so
the policy in it applies to the first command run in a checkout that has built
nothing.

## Choosing

- **Start with `i18n-kit.config.ts`.** It is checked by your editor, needs no
  build, and works on every framework the kit supports.
- **Keep `.i18n-mcp.json`** if you already have one and it is doing its job, or
  if something other than a person generates it. There is no deadline to
  migrate, and `init` still writes this format.
- **Use `nuxt.config.ts`** for descriptive policy — `context`, `glossary`,
  `localeNotes`, `translationPrompt`, `examples` — where having it beside the
  `i18n` block is worth more than it costs. Declare `protectedLocales` and
  `orphanScan` in a file the CLI reads directly.

You can use more than one. What you cannot do is declare the same key in two of
them: that is an error naming both, not a merge. See
[precedence and conflicts](/configuration/precedence).

## Limits

- The kit does not read `package.json`, `.env`, or a `config/` directory for its
  own settings. Provider credentials are the exception: an API key comes from
  the `--apiKey` flag or a provider environment variable such as
  `OPENAI_API_KEY`, never from a config file that could be committed.
- Neither file supports extending, importing or composing another kit config.
  The nearest one wins outright.
- `.i18n-mcp.json` keeps its name for compatibility even though the CLI reads it
  too, not only the MCP server.
