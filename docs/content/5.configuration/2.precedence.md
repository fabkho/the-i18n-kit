title: Precedence and Conflicts
description: A key declared in two places is an error naming both, not a silent merge — and where the kit does resolve precedence instead.
---

Declare the same key twice and the kit stops and names both files rather than
picking a winner. This page shows the error, explains why it is an error, and
lists the places where precedence *is* resolved so the distinction reads as
deliberate.

## The Rule

Two hand-written sources declaring the same key is a hard error. No merge, no
"the typed config wins", no order documented somewhere that a reader has to
remember.

```bash [Terminal]
the-i18n-cli status
```

```text
 ERROR  defaultLocale is declared in both
  /app/i18n-kit.config.ts
  /app/.i18n-mcp.json
Neither wins — a reader cannot tell which one took effect. Delete the duplicate from one of them.
```

The command exits 1 without doing any work, and the same message comes back as a
machine-readable error object carrying the code `CONFIG_ERROR`, so an agent gets
the file paths rather than a truncated stack.

Two files may both exist. What is rejected is the same key in both — the check
compares the keys that are actually present, ignoring the JSON-only `$schema`.
Split by key and both files are read: `glossary` in one and `protectedLocales`
in the other works, because the two sets are disjoint and there is nothing to
choose between.

## Why an Error Rather Than a Merge

A merge rule has to be learned, and it is learned at the worst moment — after a
value that is visibly in your repository turned out not to be the one in effect.
The failure is quiet in exactly the case that matters most: `protectedLocales`
declared in a file that lost silently protects nothing, and the only symptom is
a locale someone maintains by hand coming back machine-translated.

The kit already carries the scar. A `de-DE-formal` entry sat in a config for
months looking like it protected formal German, while the locale was in the
machine-translation target set the whole time. Precedence between two
hand-written files is another way to produce that same class of bug, and the
error is the decision not to add one.

The rule that follows: **when two sources are at the same level — both
hand-written, both in the repository, both equally visible — neither wins.**
Precedence is reserved for sources at different levels, where the ordering is
obvious without being memorized.

## Where Precedence Is Resolved

| Sources | Winner | Why the ordering is obvious |
|---|---|---|
| `--baseUrl` flag, `I18N_BASE_URL`, `providerBaseUrl` in config | Flag, then env var, then config | A flag is typed for this run; config is the standing default |
| Declared config vs. a value read out of a framework's config file | Declared | You wrote one of them for the kit specifically |
| A config in an app directory vs. one in the repository root | The nearest one, outright | The same rule ESLint and `tsconfig.json` use |
| Locale directory probing vs. a directory named in a framework config | The framework config | It states where the files are; probing guesses |

Blank values count as unset in the base URL chain, so an unset shell variable
expanding to an empty string does not shadow the config below it.

## Nuxt: The Same Rule, Checked at Build Time

`@the-i18n-kit/nuxt` runs the check during the build, where the diagnostic lands
next to the code that caused it:

```text
ERROR  "glossary" is declared both in nuxt.config.ts (i18nKit) and in
.i18n-mcp.json. Keep one — this module will not choose between them.
```

The build then fails, listing every problem it found. Set
`i18nKit.failOnInvalidConfig` to `false` to report without failing — the
diagnostics are still printed; the flag only decides whether they stop you.

The module also rejects the keys it derives. `locales`, `localeDirs` and
`defaultLocale` in `.i18n-mcp.json` are an error in a Nuxt project, because Nuxt
already answers them and keeping both means two sources of truth with no way to
tell which won.

::warning
The module's conflict check reads `.i18n-mcp.json` only — it does not look for
`i18n-kit.config.ts`. A key declared in both `nuxt.config.ts` and
`i18n-kit.config.ts` therefore does not fail the build. The CLI catches it later
and less loudly: on the artifact path, the value from the config file wins and
the CLI warns that it ignored the artifact's copy. Keep policy declared in
`nuxt.config.ts` out of your typed config until that gap closes.
::

That warn-and-let-the-file-win behavior is deliberate as a backstop rather than
as a precedence rule. It exists so an artifact generated by an older or newer
module version cannot quietly override a value you can see in your repository.

## Limits

- The conflict check is per key, not per subkey. Declaring `glossary` in both
  files is an error even when the two objects contain different terms; there is
  no per-term merge.
- The error names the two files and the offending keys, not the line numbers.
- Multiple `i18n-kit.config.*` files in one directory are a warning rather than
  an error: the first by extension order is used and the others are named as
  ignored.
- Nothing checks across directories. A config in an app directory shadows the
  root one silently — the root file is not read at all, so a key in it cannot
  conflict with anything.
