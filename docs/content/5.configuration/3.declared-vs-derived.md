---
title: Declared vs. Derived Configuration
description: Config a person writes for the kit, config read out of a framework's own files, and why a broken one of each is treated differently.
---

The kit works from two kinds of configuration: **declared config**, which you
write for the kit, and **derived config**, which it reads out of files your
framework already owns. Knowing which is which tells you what you have to write
down, what happens when a file cannot be read, and which value wins.

## The Two Kinds

**Declared config** is everything the tool cannot see for itself:
project context, a glossary, per-locale notes, which locales are protected. It
lives in `i18n-kit.config.ts`, `.i18n-mcp.json` or the `i18nKit` block of
`nuxt.config.ts` — see [where configuration lives](/configuration/where-config-lives).

**Derived config** is what your project already states somewhere: which locales
exist, which one is the reference, where the locale files are, and which
**layers** — scoped locale directories, whether that is a Nuxt layer, a
workspace package, a shared UI library or an app in a monorepo — contribute to
an app.

The kit reads the following, in each case executing the file rather than
pattern-matching it:

| Setup | Read from | Gives |
|---|---|---|
| Nuxt with `@the-i18n-kit/nuxt` | `.nuxt/i18n-kit.json`, published during the build | Locales, default locale, fallback locale, layer directories |
| next-intl | `src/i18n/routing.ts` — `defineRouting({ ... })` | `locales`, `defaultLocale` |
| next-translate | `i18n.js` | `locales`, `defaultLocale` |
| Next.js Pages Router | `next.config.{ts,js,mjs}` — the `i18n` block | `locales`, `defaultLocale` |
| Vue with `@intlify/unplugin-vue-i18n` | `vite.config.{ts,js}` — the plugin's `include` | Locale directories |

The Next.js sources are tried in that order: most specifically about i18n first,
which also puts the file likeliest to throw last. When none of them yields
anything, the adapter falls back to probing a fixed list of candidate
directories, which is what every adapter did before it could execute
TypeScript at all.

A framework config is only ever executed while resolving a project, never while
detecting one — detection runs against every project the CLI is pointed at.

## Declared Beats Derived

Where both have an opinion, the value you declared wins. Pinning the reference
locale regardless of what any framework config says:

```ts [i18n-kit.config.ts]
import { defineI18nKitConfig } from '@the-i18n-kit/cli/config'

export default defineI18nKitConfig({
  defaultLocale: 'en',
})
```

The resolution order for `defaultLocale` in the React adapter is declared value,
then the framework config, then the first discovered locale — so declaring it
also removes the last of those, which is a guess about directory order.

Nuxt inverts the ownership for the three keys it can answer itself.
`@the-i18n-kit/nuxt` rejects `locales`, `localeDirs` and `defaultLocale` in
`.i18n-mcp.json` with a build error, because Nuxt resolves them and a second
hand-written copy is a source of truth with no tiebreak.

## Why One Throws and the Other Warns

A broken `i18n-kit.config.ts` fails the command. A framework config that cannot
be executed prints a warning and the command continues. That looks inconsistent
and is not.

**A framework config belongs to another tool.** A real `next.config.js` is
wrapped in `withNextIntl(...)` or `withSentryConfig(...)` and needs the right
environment variables and installed plugins to run at all. A `vite.config.ts`
needs Vite and every plugin it imports. Failing to execute one of those is
common, is not your fault, and has a reasonable answer: fall back to the
directory probing that was the only behavior available before. So it warns and
falls back:

```text
 WARN  Could not read /app/src/i18n/routing.ts: Cannot find module 'some-missing-pkg'.
Falling back to directory detection — declare the value in i18n-kit.config.ts to be sure of it.
```

The command then completes normally. The same rule covers the Nuxt artifact:
absent, malformed, written by a version this CLI does not understand, or older
than the `nuxt.config.ts` it claims to describe — each is a warning and a
fallback to loading the app through Nuxt. A module that cannot be trusted must
not be able to break a project that worked without it.

**A kit config exists only for the kit.** Nothing else reads
`i18n-kit.config.ts`, so there is no fallback that preserves its meaning.
Carrying on without it means applying none of the policy you can see in your
repository, which is the failure the file was added to prevent. So it throws,
naming the file:

```text
 ERROR  Failed to load /app/i18n-kit.config.ts: Cannot find module '@the-i18n-kit/cli/config'
```

The same applies to a config that loads but is wrong: an unknown key, a
misspelled field or a config exported as anything other than a default export
fails validation and the command exits 1 rather than proceeding with a partial
config.

The asymmetry in one line: **falling back to detection is a reasonable answer to
an unreadable framework config, and there is no reasonable answer to an
unreadable kit config.**

## Limits

- Derived config is read per project directory. It cannot tell you why a value
  is what it is beyond the log line naming the file it came from — run with
  debug logging when a locale set surprises you.
- Only the sources in the table are read. A project declaring locales anywhere
  else falls back to directory probing, and declaring the value yourself is the
  fix.
- The Vue reader takes the plugin's `include` option. A project that configures
  the plugin dynamically, or from a value the recorder cannot observe, gets
  directory probing instead.
- Deriving a value never rewrites your files. The kit reads them; it does not
  offer to normalize them.
